# Review of cevheri/keycloak-custom-event-listener

Reviewed on 2026-09-25 at commit `3c2a59e29d05123ed3ee3fda7d37656b04084a80` using its [listener](https://github.com/cevheri/keycloak-custom-event-listener/blob/3c2a59e29d05123ed3ee3fda7d37656b04084a80/src/main/java/com/cevher/keycloak/CustomEventListenerProvider.java), [HTTP client](https://github.com/cevheri/keycloak-custom-event-listener/blob/3c2a59e29d05123ed3ee3fda7d37656b04084a80/src/main/java/com/cevher/keycloak/Client.java) and [database script](https://github.com/cevheri/keycloak-custom-event-listener/blob/3c2a59e29d05123ed3ee3fda7d37656b04084a80/initdb/init.sql).

The listener handles REGISTER and admin USER CREATE, looks up the user through the session model, and synchronously posts a webhook. It catches delivery exceptions and logs them. There is no durable retry state, commit coordination or downstream deduplication. Inference from that control flow: a failed send can leave a committed account without a delivered notification; a successful webhook before a later rollback can expose an operation that did not commit. Restart cannot recover unsent events. Its `initdb` SQL provisions the Keycloak role/database; it does not install extension delivery tables.

It avoids custom JPA registration because it does not implement transactional delivery. Its event listener still uses the same Keycloak event SPI, which [Keycloak marks internal](https://github.com/keycloak/keycloak/blob/26.7.4/server-spi-private/src/main/java/org/keycloak/events/EventListenerSpi.java). Therefore it offers fewer persistence integration points but not comparable guarantees.

Our recommended approach remains the outbox in Keycloak's existing database transaction, with localized integration points and runtime upgrade tests. [Custom JPA registration is documented but unsupported](https://www.keycloak.org/docs/latest/server_development/#_extensions_jpa); this limitation remains explicit. The linked listener does not provide a stable API substitute for that transaction boundary.

Alternatives require a different operational architecture: database change capture from a durable transactional record, or an upstream-supported durable event export. Moving the send to an after-commit callback alone leaves a process-crash gap. A separate database/HTTP endpoint cannot atomically commit with Keycloak without a distributed transaction or an equivalent durable source. Polling the admin API can reconcile current state but cannot reconstruct every intermediate event. We have not replaced the outbox with any of those weaker mechanisms.
